Next, train the model using a https://docs.ultralytics.com/models/yolov5/[YOLOv5,window=_blank] object-detection model and the provided fedora images. The training process runs in a pipeline that uses OpenShift resource scaling.

After training, the model is exported in ONNX format to your S3 bucket on **ODF** (OpenShift Data Foundation). You can then deploy it to an inference service on **OpenShift AI** and serve it to the application.

[NOTE]
====
Inference in AI is the process of using a trained model to make a prediction or generate a response from new, live data. If training is the "studying" phase, inference is the "application" phase, where the model uses what it has learned to do its job.
====

=== The Training Images

To stay within the available resources, we provide about 100 images of a Red Hat fedora and their label metadata to train the base model.

[NOTE]
====
In object detection, labeling is the human annotation of raw images. Bounding boxes are drawn around specific objects, and each object receives a class label, such as "car", "person", "tree", or "fedora". This teaches the base model to recognize a new class of objects.
====

Because the training images deliberately contain little variation, the model will recognize this particular fedora well but may struggle with slightly different ones. This is called "overfitting" and is usually avoided, but it is acceptable for this demonstration.

To see what the images look like, navigate in JupyterLab to `object-detection-training-pvc/custom_training_images/fedora/images/` and open a few images. You will see slight variations of a Red Hat fedora against different backgrounds.

image::training-image.png[link=self]

Bounding-box labels tell the model which part of an image contains the fedora. This data is stored in the `labels` folder. Each text file corresponds to an image and contains the coordinates that define its bounding box.

=== Model Training

[NOTE]
====
Model accuracy is limited by the available compute. To fit the data center and physical robot constraints, the base-model size, training epochs, batch size, and number of training images are intentionally limited. You can change these values, but more epochs or images may substantially increase training time without improving the result.

These trade-offs are common for edge deployments, where model accuracy must be balanced against model size and runtime requirements.

Set realistic expectations for the model and avoid spending too much time fine-tuning it.

With these constraints in mind, let's train the model.
====

== Model Serving
You now have a trained model for object recognition. To actually use the model we will deploy it into **OpenShift AI** Model Serving, which will make it available via an API.

=== Model Runtime

First, configure a model server:

* Switch back to the OpenShift AI browser tab
* Click **Projects** in the main menu and make sure that `{user}-ai` is selected
* Select the **Deployments** tab
* Click on **Deploy model**

== Model Testing

Now it's time to finally test the model. And since we are Data Scientists here, we'll run the first tests to see how the model is performing in our JupyterLab Workbench.

* Copy the external inference endpoint URL that is published through an OpenShift Route (and save it somewhere)
+
image::copy-inference-url.png[link=self]

* Copy the token for the endpoint by expanding the `ovms` model-server entry
+
image::copy-token.png[link=self]

* Back in your JupyterLab Workbench in the `object-detection-notebooks` directory, open the `online-scoring.ipynb` notebook
* Look for the variables `prediction_url` and `token`
+
[source,python]
----
prediction_url = 'REPLACE_ME'
token = 'REPLACE_ME'
----
* Paste the inference endpoint URL and the token you copied before into the placeholders

* Run the full notebook (the button with the two play icons in the top menu)
+
image::run-full-notebook.png[link=self]

* Confirm to **Restart the Kernel**

You will see any identified classes with bounding boxes and confidence score at the end of the notebook.

You can test the model with images in the `sample-images` folder or upload your own. Take pictures of the fedora on the floor with a laptop or smartphone, then upload them to the `sample-images` folder. Update the image name in `image_path` before running the notebook again. Use square images when possible; otherwise, bounding boxes may be drawn in the wrong location.

[TIP]
====
If you see multiple bounding boxes around a fedora, you may need to filter out lower-scoring detections. By default, the code filters out detections with a confidence score lower than `0.3`. Search for `+conf_thres=0.3+`, increase the value, and rerun the notebook.
====
